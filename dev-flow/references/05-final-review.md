# 05 完成评审阶段（你不参与）

## 目标

功能做完了，但还不能交付。用 3 路 AI 评审确认「它真的对、真的能用、没有把别的地方弄坏」。产出 `review-final.md`。

## 分批综合评审

阶段性综合评审**按批触发**：每完成 **6–8 张落地单**为一批（项目可在批次开始时写定具体阈值，但不建议超过 8 张）。每批：

- 列出本批纳入的落地单/提交范围（与 `09-conductor.md` §11 的「每轮汇报三块」第三块同源）；
- 写明本批重点检查项（新增风险面、跨模块接口、NFR、回归敏感区）；
- 结论落 `review-final.md` 的批次记录；工单细节留在 `specs/`，用户汇报只给批次结论与待拍板项。

批量较小时可合并批次，但不能跳过——批次是综合评审的触发单位，不是可选项。

## 输入

- `spec.md`、`design.md`、`tasks.md`、`traceability.md`
- 完整 diff
- 测试输出/证据
- 已知限制/决策记录

## 用哪个技能

| 情况 | 技能 | 说明 |
| --- | --- | --- |
| 评审引擎 | `code-review` | 规范轴 + 规格轴，fresh subagents，12 条 Fowler 坏味道 |
| 请求评审 | `requesting-code-review` | 怎么把 spec/diff/证据打包给评审者 |
| 接收评审 | `receiving-code-review` | 先验证再改、禁表演式认同、逐项测试、YAGNI 反查、允许 pushback |
| 完成验证 | `verification-before-completion` | 无新鲜证据不称完成；命令+退出码+逐条清单 |
| 3 路评审 | 3 个并行 agent + 裁判 | 见下 |

## 3 路评审（并行，默认异构）

跨会话派评审会话时，按 `04-implement.md` 多会话上下文治理执行（执行细节落盘，不回灌调度）。本册的 3 路 + 裁判是**功能级完成评审，不因 04 的风险档降级**（04 的风险分档只管工单级节点对标）；3 路本身即 3 个评审者，已满足 ≥2 交叉口径。

**默认异构，项目配置可同型号**：同一模型开两个对话互审，训练数据/偏好/盲区高度相关，审得出笔误、审不出系统性盲点——所以 3 路默认换模型家族。项目 `.dev-flow.json` 的 `models.finalReview` 显式指定（1 项=三路同型号、3 项=逐路指定）时以配置为准，允许三路同型号（三种审查视角仍互补），但必须在报告校准记录声明「按项目配置三路同型号」。裁判模型按 `models.finalJudge` 取，不再自行「再换一个」；对应槽位未配置 → 停下问用户，不静默用默认（见 09 §1 运行期取模）。既未配置异构、又做不到多模型时（如单一模型环境），必须在报告里声明并加倍人工抽查。意见分三档（必改/建议/不成立），判「不成立」写理由；方向性分歧上抛用户；两三轮封顶，超过说明是方向性问题。

**入口先跑销单机检（硬拦）**：`node <技能目录>/scripts/issue-audit.mjs --root <项目根> --feature <name> --phase final-review`——状态行规范/扫描范围/done 工单勾选/自签收/设计决策映射节落点/issue↔tasks↔traceability 状态同步/豁免签名七查 + 项目声明的台账对账命令（`state.json` 的 `gates.coverageReconcile`）。任一红即先修再进评审；机检不过不得开评审。

### 评审 1：设计/需求符合性

- 每条 AC 是否有证据？
- **逐条对证据**：每张 done 工单的验收清单逐项核对——勾选项必须指向可查证据（测试名/文件行/提交/台账条目）；空勾、复述式勾选（把判据抄一遍当证据）视同未勾（实战案例：曾有工单 0/7 勾选自签收过关）。勾选附**如实残留注记**且已登记台账/延后项的＝合格（诚实边界不是空勾）。
- 有没有少做（缺功能）或多做（scope creep）？
- 设计里的失败模式/NFR 六条有没有落地？
- **偏差登记无滞留**：`design-deviation.md` 无「待裁决」行（有则先闭环裁决再进评审）；「已裁决接回」行有接回 owner 与批次。
- **覆盖类台账机器对账**：覆盖矩阵/端口表/映射表等台账类产物，对账脚本的最少强制项（缺一即 blocking）：①解析台账本体（任一端为手抄清单即不合格，手抄+源数据双录必漂移）；②`status=covered` 行的实现/producer 路径在仓库内实际存在；③行内 `tests`/`evidence` 引用可逐项解析到真实符号（文件/测试函数）；④有代码注册表时双向差集为空。**证据形态**：脚本路径（入库可重复运行）+ 对账命令 + 退出码 + 红行明细 + 一次**负向证明**（人为制造不存在路径/测试引用，展示转红后复原）——口头声称有脚本视同未做。**承接与出口**：脚本归项目侧、实现期建，评审只验「存在+能跑红绿」；源数据不可机读须先机器化，或登记延后项并在 `review-final.md` 附人工核验清单（列核对项与命令），不得以「无脚本」放行；`draft`/代表性台账的 covered 行不得作为完成证据。对账输出须打印「已对账行数 / 声明总数 / 各状态计数」，防「全标 covered」与草稿空绿（实战案例：曾有覆盖表全标 covered 但实现不存在、行内引用不存在的测试，元数据自相矛盾而机器零拦截）。
- 输出：`blocking` 必须修 / `suggestion` 建议。

### 评审 2：正确性/架构

- 边界/异常/并发/错误处理是否正确？
- 有没有绕过接口、依赖方向违规、临时补丁？
- **契约/端口消费者**：设计定义的 Port/Protocol 是否有生产代码消费者（零消费者＝死契约，接线或已登记偏差）；适配器私有结构有没有僭越成事实契约（私有字典/字段成了实际标准而契约层空转）。
- 性能/内存/阻塞是否符合设计预算？
- 安全/信任边界（IPC/文件 IO/插件/更新链）有没有问题？
- **能力/权限影响（硬项）**：diff 出现设置读写（`getSetting`/`setSetting` 类）、`plugin-sql`/`fs`/`http`/`dialog`/`shell` 等插件调用、`invoke` 自定义命令、跨窗口事件/数据访问时，必须核对**目标窗口/进程**的 capability/permission 清单（Tauri `src-tauri/capabilities/*.json`、Capacitor 插件配置、Electron preload allowlist），并在本路报告写一行「**能力影响：已核对 <文件清单>（结论）/ 无需变更（理由）**」——缺行视为该路评审不完整（快查表见 `references/04-implement.md`；核对输入＝派工令「文件地盘→关联只读检查」列出的文件，无派工令的形态 A/C 直接查仓库 capability/manifest 配置）。
- 输出：`blocking` / `suggestion`。

### 评审 3：测试与回归

- 正常/边界/异常场景是否覆盖？
- 测试是否证明行为，而不是证明实现？
- **测试证明力（反空转，必查）**：凡证明力依赖「X 曾进入被测链路」的断言——典型如「X 不出现/不泄露/不调用/不乱序/被过滤/被重排」，以及性质类变相写法（`count(x)==0`、`filtered==[]`）——必须先证明 X 确实在被测链路里存在。入链证据判据：捕获点必须位于被测链路的**真实注入路径**（替换生产工厂/加载器，构造链全程真跑，如 `captured["api_key"] == secret`）；允许 mock 外部边界（SDK/网络），不许 mock 被测链路段；自造调用再断言 captured 相等的自证不算入链。三例反面教材：① 凭据测试 secret 没进被测链路（早退分支绕过 config 读取，`assert secret not in ...` 恒真）；② 凭据测试构造适配器根本没传 api_key；③ 乱序测试实际喂顺序数据（判据空转）。
- 手抄清单/双录型「测试」只证明抄件一致（同义反复），与评审 1「覆盖类台账机器对账」同源，须按该条口径处理。
- 旧功能/旧数据有没有回归？
- 接线（入口/IPC/UI/资源）有没有验证？
- **能力面改动的测试证明力（硬项）**：新增窗口/进程/权限/数据路径时，必须有真实语境证据——真实窗口标签与真实能力集下的 E2E 或能力配置断言（见 `references/11-testing.md` 真实上下文测试：硬底线至少一条，通用做法两条全做）；主窗口/测试窗口的 E2E 不能替代，单测全绿不构成能力面改动的放行证据；真实语境证据为零＝`blocking`，只落地一条而未记录另一条不可行的理由同样 `blocking`。
- 输出：`blocking` / `suggestion`。

## 裁判

- 合并三份清单，去重。
- 分四类：必须修 / 建议 / 误报 / 挑刺。
- 只有「必须修」能阻断。
- 必须修修完后，再跑一轮；连续两轮无新增必须修才算稳定。
- 评审者必须声明「查了什么、没查什么」；没声明视为不完整。

## 评审者校准（防「三个 agent 说没问题」的剧场）

- 3 路评审**默认异构**；裁判按 `models.finalJudge` 配置取。项目 `models.finalReview` 显式指定同型号时以配置为准，并在校准记录声明；既未配置异构、又做不到多模型时（如单一模型环境），必须在报告里声明，且人工抽查加倍。
- 已知坏样例库（至少 5 个）在维护仓 `calibration/`；运行包不含时按下方通用清单评审：
  1. 代码在、入口没注册；
  2. 降级实现（承诺 A 做了 B）；
  3. 越过架构边界（乱 import/绕接口）；
  4. 测试同义反复/只测实现；
  5. NFR 违规（大文件卡死/编码错/旧数据打不开）。
- **每轮评审记录**：模型、命中的坏样例、误报数，写入 `review-final.md` 的校准记录。
- **召回率低于 80% → 不允许把该评审结果当门禁**；先调提示词/换模型，再重跑。
- 每个阶段至少一次**人工抽查** 1-2 条发现，确认不是评审剧场。

## 门禁

- 无「必须修」。
- `issue-audit` 全绿（`--phase final-review`，退出码 0）。存量历史红（如 git 历史不可改的自签收旧案）只能经独立评审/档案会话在工单「历史」段写 `issue-audit 豁免：…（独立重签：<报告路径>）` 降级为 NOTE：**必须带机器可识别签名 + 仓库内可打开的报告路径**；工人自写豁免、无签名、路径不存在一律判红，不降级。豁免清单须列入 `review-final.md` 的「issue-audit 豁免清单」节供用户过目。
- 状态同步三表一致：issue 状态行 ↔ `tasks.md` 索引行 ↔ `traceability.md` AC/决策行；`done` 工单不得对应 `planned/⬜`。
- `verification-before-completion` 的证据齐全。
- 能力面硬项：触及能力面（设置读写/插件调用/自定义命令/跨窗口事件或数据访问）的评审，评审 2/3 缺「能力影响」行、或评审 3 缺真实上下文测试证据（真实窗口标签与真实能力集下的 E2E 或能力配置断言，硬底线至少一条、默认两条全做，见 `references/11-testing.md` §9）→ 门禁不过。
- 校准记录在案且召回达标（或已声明降级）。
- 更新状态：`gates.finalReviewed=true`，`stage=acceptance`。

## 产出

`specs/<feature>/review-final.md`，包含：

- 3 路原始发现（含严重级别、证据、复现方法）
- 裁判分类与最终阻断清单
- 修复记录（哪条、怎么修、哪个提交/证据）
- 两轮收敛记录
- 未修的建议/已知限制
- **校准记录**：模型、命中坏样例、误报数、召回率结论

## 常见错误

| 错误 | 后果 | 纠正 |
| --- | --- | --- |
| 只跑一个评审 | 自己批自己 | 3 路 + 裁判 |
| 评审者没看 spec | 只审代码风格 | 评审输入必须含 spec/AC |
| 评审发现没证据 | 无法复现/误报 | blocking 必须带证据+复现 |
| 修完不复审 | 修出新问题 | 修完再跑一轮 |
| 把建议当必须修 | 无限打磨 | 只有 blocking 阻断 |
| 不记录校准 | 评审质量不可知 | 每轮记模型/命中/误报 |

# 08 TaskChron 同步（驾驶舱，单向）

## 定位

**本地 `specs/<feature>/` 是执行真相；TaskChron 是给人看的驾驶舱。** dev-flow 单向写 TaskChron，TaskChron 永远不反向改 `specs/`。

**开关**：`.dev-flow.json` 的 `taskchron.mode`：`on` 强制、`off` 关闭、`auto`（默认）看宿主是否有 TaskChron MCP。关闭或 MCP 不可达时跳过本册全部动作，本地 `state.json` 继续，并在回复中声明「时记未同步」。

## 环节化口径

环节级进度看板比工单级明细账更容易看清总进度。本节所称「环节」= 时记看板上 epic/批次级的子任务，不是流程步骤；工单完成仍叫「销单」，调度接收工人报告仍叫「收账」。

- **一个功能 = 一个父任务 + 5–10 个环节子任务（epic/批次级）**。环节是能独立讲清「完成后用户能看到什么」的一批工单，不是一张工单；存量功能按真实 epic 数划分，不硬拆凑数。
- **标题模板**：`<feature短名> <环节号>：<一句大白话结果>`。例：`订单导出 E1：导出链路打通，用户三步内完成导出`。
- **备注**：包含哪些工单号（如 `T-01/T-02/T-03`）+ 完成后用户能看到什么 + `specs/<feature>/` 路径。
- **三问口径**：每个环节的标题与备注必须回答「这个环节是干什么的、做完有什么用、包含哪几张工单」；不许堆术语。用户侧只看环节进度，工单细节留在 `specs/`。
- **工单细节不入时记**：指 feature 工单；留在 `specs/<feature>/tasks.md`、`issues/T-XX.md` 与 `evidence/`。计划外工作线补记与 triage 排期条目仍按原规则，不在此限。
- **调度动作不建条目**：收账、派工、裁决都不是交付，不建时记任务。**该口径只约束「不建工单级条目」，不禁环节状态维护**——收账触发的刷新环节备注、勾环节、父任务收口是必做动作，不得以「调度不入时记」为由跳过。
- **项目/对接人**：用 `add_subtask` 建会自动继承父任务；用 `bulk_create_tasks` 建需每条显式带 `project`/`contacts`（建后用 `update_task` 也可回填），不依赖自动继承。
- **旧账保留**：此前已建的工单级子任务与阶段里程碑是历史账，保留不删；新功能不再新增这两种粒度。旧功能如需补录，可用 `scripts/taskchron-payload.mjs` 的 6 阶段里程碑载荷一次性补录（历史/降级）；已环节化的功能不再补录。旧账不计入新环节口径（App 若仍挂在父任务下，进度以环节子集为准）。

## 同步什么

父任务 + 环节子任务。环节在 03 工单阶段与 `tasks.md` 同批划定：3 路审核通过、`gates.ticketsReviewed=true` 后、进入实现前，按已定稿的拆单建环节。环节映射记录落在 03 阶段产物（可参照现有项目的 `tasks.md` T↔Epic 分组；新 feature 暂由 03 主流程在 `state.json`/`handoff` 记「环节 → 包含工单 → 时记任务 ID」，不改 `tasks.md` 四列索引契约）。

| 事件 | 时记动作 |
| --- | --- |
| 设计签字后、03 工单拆分产出 `tasks.md`，3 路审核通过（`gates.ticketsReviewed=true`） | 父任务（若尚未建）与 5–10 个环节子任务一次建齐（存量功能按真实 epic 数）：父任务先 `create_task`，环节子任务用 `bulk_create_tasks` 挂 `parent_task_id`（≤50 条/批），每条显式带 `project`/`contacts`。建齐后把父任务 ID 与各环节任务 ID 回填 `state.json` 的 `taskchron` 映射（见下节） |
| 04 任一工单收账（**非环节最后一张**） | **刷新所属环节备注**：已完成/总数 + 一句大白话进度（如 `T-01/T-03 完成，剩 T-02——导出模板已好，样式对接中`），只 `update_task` 改备注，**不改状态**。这是收账必做项，不是可选优化 |
| 04 某个环节内最后一张工单收账（销单并留证） | 勾该环节：`set_task_status status=done`（`completed_at` 用收账时刻），不逐工单勾。**最后一个环节例外：最后一张工单收账后先不勾，等 05/06 出口满足后再勾** |
| 05 评审/返工 | 若「必须修」导致某环节内工单返工，把该环节改回进行中并备注原因；修复收账后再勾 |
| 全部环节完成 | 父任务同批 `set_task_status status=done`。**最后一个环节的出口必须覆盖 05 完成评审与 06 实机验收；验收作为最后环节出口的一部分**；「全部环节完成」按该出口全部满足计，避免父任务早于评审/验收变绿 |
| 验收通过 | 不单建「验收通过」里程碑；验收作为最后环节出口的一部分，按上一条勾环节/收口父任务 |
| 环节拆分/合并/取消 | 随 `tasks.md` 走；时记侧改标题/备注或标「已取消」，不删除；存量旧账保留历史，不计入新环节口径（App 若仍挂在父任务下，进度以环节子集为准） |

**执行者**：有路由编排（形态 B）时，建环节（03 审核通过后）、刷新环节备注与勾环节/父任务收口（收账时）由**调度会话**承担（见 09 收账口径）；无调度会话（形态 A/C）由本会话承担。工人会话只做销单、changelog、计划外补记，不碰时记环节。

流程门禁（需求/设计/工单/开发/评审/验收）仍是 `state.json` 的流程判断依据；时记环节勾选反映开发进度，父任务收口按上表与最后环节出口对齐。

## 环节映射与新鲜度锚点（state.json 的 taskchron 块）

环节 → 时记任务的映射与新鲜度判断都落在 `specs/<feature>/state.json` 的 `taskchron` 块（03 建环节批后回填，`templates/state.json` 有结构示例）：

```json
"taskchron": {
  "parentId": "<时记父任务 ID>",
  "epics": {
    "E1": { "taskId": "<环节子任务 ID>", "tickets": ["T-01", "T-02"] }
  },
  "lastSyncedAt": "<最后一次成功同步时记的 ISO 时刻>"
}
```

- **`parentId` / `epics[].taskId`**：定位时记任务，收账刷新备注、勾环节、父任务收口都从这里取 ID，不再翻聊天记录或猜任务名。
- **`epics[].tickets`**：该环节包含的工单号，用于算「已完成/总数」与判断「是否环节最后一张」。
- **`lastSyncedAt`**：新鲜度锚点。**新鲜度规则：收账/收口时，若最新销单时刻 > `lastSyncedAt`，判「时记过期」——必须完成同步（刷新备注/勾环节）后才能收尾本轮；同步成功后把本次时刻写回 `lastSyncedAt`**。没有时间可比（如环节刚建、无销单）不判过期。
- **硬拦（机器化）**：上述新鲜度规则由 `scripts/issue-audit.mjs` 第 8 项门禁机器校验，**只在 `--phase final-review`（`wt:done` 全量审计）生效**——最新销单提交时刻（翻 done 提交的提交时间，绝对时间比较）> `lastSyncedAt` 直接红：`时记过期：先刷新所属环节/父任务备注并写回 lastSyncedAt`。staged/pre-commit（tickets 口径）不查，日常提交不受拦；无 `taskchron` 块/字段（旧 feature）、`taskchron.mode=off`、git 无可考销单提交 → 自动跳过不误伤；纯离线 git/state 判定，**不要求 TaskChron MCP 可达**（MCP 不可达不豁免红也不额外拦）。**回退方法：按本册事件表刷新所属环节备注/勾好环节后，把同步完成时刻写回 `state.json` 的 `taskchron.lastSyncedAt`，重跑 `wt:done` 即转绿**；没同步就伪写锚点，会在下一笔销单后再次变红。
- 旧 feature 的 state 没有 `taskchron` 块时，按原有映射记录（`tasks.md`/`handoff`）执行，顺手补建该块即可，不强制迁移。

## 怎么同步

1. **建环节批（03 工单阶段）**：3 路审核通过、`gates.ticketsReviewed=true` 后、进入实现前，按上节指定的环节映射记录（`tasks.md` 或 `state.json`/`handoff`）整理载荷，父任务不存在先建，环节子任务批量挂 `parent_task_id`；标题/备注按上节模板。时记任务 ID 回填同一映射记录——新 feature 统一回填 `state.json` 的 `taskchron` 块。存量功能补建环节时，`completed_at` 用真实收账时刻、`created_at` 回填环节实际开始日（或备注「YYYY-MM-DD 补建」），避免时间倒挂。
2. **勾选批（04/05）**：完成一个环节勾一个，不逐工单勾；必须等环节内最后一张工单收账后再勾（防止「工单做完但环节验收没过」提前变绿）；**最后一个环节等 05/06 出口满足后再勾**；05 返工按上表回退。非最后一张的收账按事件表刷新所属环节备注。每次同步成功后写回 `taskchron.lastSyncedAt`。
3. **收口批**：全部环节完成且最后环节出口（含评审/验收）满足后父任务 done；写完后 `get_activity_logs` 对账一次。收口前按新鲜度规则检查，过期先补同步再收口。
4. **补记批**：计划外交付按项目规范的补记批（工作线聚合）处理，不建 feature 环节；调度/派工/裁决不建条目。
5. **旧功能补录**：尚未环节化的旧功能可用 6 阶段里程碑载荷补录（历史/降级）；已环节化的功能不要再用该载荷重复建条目。

## 降级规则

- **MCP 不可达**：跳过同步，本地 `state.json` 继续；在回复中声明「TaskChron 未同步」。恢复后用同一映射记录/载荷补同步。新鲜度过期遇 MCP 不可达：按本规则声明跳过当轮收尾，**不伪写 `lastSyncedAt`**；恢复后先补同步再继续收账。
- **部分失败**：记录失败项，下轮重试；不回滚已写入条目。
- **不反向**：即使 TaskChron 里有人改了任务，也不把改动带回 `specs/`。

## 可选项

- **工单级同步**：已废止（新口径）。工单细节留在 `tasks.md`/`issues/`/`evidence/`，不建时记条目。
- **triage 的 `ready-for-agent` 条目**：可按需同步为 TaskChron 任务（截止+预估+人话三句），供用户排期；triage 条目是分诊排期项，不是 feature 工单；一旦进入某 feature，只挂该 feature 的环节，不另建 ticket 级条目。
- **依赖标注**：多功能并行时，用 `dependsOnFeatures` 在环节备注里写明「依赖 <feature> 的 <环节>」；**不自动改 TaskChron 优先级**，排序交给用户。

## 红线

- 不用 TaskChron 替代 `state.json`/本地 issue 做流程判断；
- 不同步敏感信息（凭据、日志原文）进备注；
- 同步失败不阻塞流程本身。

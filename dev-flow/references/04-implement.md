# 04 实现阶段

## 目标

按工单逐节点实现，每个节点都对照工单和设计，发现偏离立刻停。产出代码、测试、证据。

## 输入

- `specs/<feature>/issues/`（工单文件：交付、验证命令、AC 回指）
- `tasks.md`（索引和阻塞图）
- `design.md`（接口、失败模式、非功能）
- `traceability.md`
- 项目槽位/门禁规则

## 用哪个技能

| 情况 | 技能 | 说明 |
| --- | --- | --- |
| 主执行引擎 | `subagent-driven-development` | 每任务 fresh subagent、规格符合性 + 代码质量两段评审、fix loop |
| 测试 | `tdd`（Matt） | 接缝、红绿、反模式；用 Superpowers 的 `test-driven-development` 铁律兜底 |
| 疑难 bug | `diagnosing-bugs` | 先造红灯反馈回路，再最小化、假设、单变量验证 |
| 不要用 | `executing-plans` | 与 SDD 重叠且更弱 |

**不使用 `implement`/`implement-spec`**：前者是 SDD+TDD+review 的薄包装，后者建集成分支/合并与槽位冲突。单票就用 SDD 逐票推进；需要并行就用 `dispatching-parallel-agents` 派多个 SDD 子代理，工单图里 Blocked by 已经定义了能并行哪些。

测试体系（改动类型→测试要求、两级门禁、证据格式、抖动/断言治理）见 `references/11-testing.md`；本册只保留节点级流程与评审分档。

## 每个节点的流程

1. **复述工单**：标题 + 验收清单 + Blocked by 是否已落定。
2. **确认接缝**：这次在哪个公共接口测？每个接缝能抓什么/会漏什么？
3. **先写失败测试**：看它红，再写最小实现。
4. **跑验证命令**：把命令、退出码、输出存到 `evidence/`。
5. **节点对标**（检查员只拿工单 + 设计 + diff + 测试输出）：
   - 工单要求做了没有？
   - 设计接口有没有被绕过？
   - 有没有降级实现、假接线、顺手重构？
   - 测试是不是真的证明了行为？
   - 接线有没有漏：入口/路由/事件/IPC 单源宏注册/UI/资源清单/安装包？
   - 有没有回归风险（旧功能、旧数据）？
   - **设计决策落点对账**：工单「覆盖」行声称的设计决策 ID（裸格式 `D60`），兑现了没有？未兑现的必须已登记 `design-deviation.md`——「未实现又未登记」不算完成（销单时 `issue-audit` 机器对账，见门禁）。
6. **偏离处理**：
   - 实现细节问题：就地修，记录到 `decision-log.md`。
   - 设计级问题：停，先在 `design-deviation.md` 登记偏差（决策 ID/偏差内容/理由/裁决人/状态），再回设计阶段让用户拍板——不登记的偏差无效，后续工单会把绕行当事实标准固化。
   - 工单判据错了：停，回工单阶段重拆。
7. **更新状态**：每完成一张工单，更新 `state.json` 的 `currentTicket`、issue 文件的 `**状态**` 行（首 token 只能是 `pending|in-progress|done|blocked|cancelled`，说明放括号），同步 `tasks.md` 索引行与 `traceability.md` 对应行，并把证据登记进 `traceability.md`。置 done 前工单「**节点对标结论**」节必须填齐（模板固定节：评审执行者/必须修清单/处置记录三项非空）——单级评审的产物落点，销单 diff 可机检。分工：节点对标结论＝工单级评审记录（落工单文件），`review-final.md`＝功能级 3 路评审（落独立文件），互不替代、不重复登记；工单「历史」段只记时间线（创建/完成/提交号），不复述评审结论与处置。

## 多会话拓扑（谁在哪个会话干什么）

同一套节点流程有三种部署形态。**先认形态，再开工**：每个环节「谁实现、谁评审、谁收账」由形态表钉死，不允许口头默认。派单令写明形态即从之；未写明默认形态 A。跨会话派单（形态 B）的**线间协议**——派工令六字段、回传报告块（工人完工只落 `specs/<feature>/evidence/<ticket>-report.md` 头部并提交，不调 SendToSession，见 09 §3）、调度台账、看门狗巡检——见 `references/09-conductor.md`（路由编排层正本）：本节管节点级归属，09 管线间协议，两册叠加使用。工人会话的用户/路由可见名带 `S<N>-` 槽位前缀（领取槽位后补，规则见 09 §1 会话命名）。派工/评审前按项目 `.dev-flow.json` 的 `models` 取对应槽位（工人 `worker.default`/`worker.light`、检查员 `inspector`、工单评审 `ticketReview`/`ticketJudge`、完成评审 `finalReview`/`finalJudge`）；**该槽位未配置 → 停下问用户，不静默用默认**；1–3 段是否派前期工人由 `models.early` 决定（见 09 §1 运行期取模）。

### 三种形态与逐环节归属

| 环节 | A 单会话 SDD（一会话全兼） | B 跨会话派单（调度 + 工人 + 检查员） | C 单人（用户亲写） |
| --- | --- | --- | --- |
| 实现 | 本会话 SDD 子代理逐节点 | 工人会话（每单或每批一个会话） | 用户会话亲自写 |
| 节点对标（检查员评审） | 按风险档执行评审铁律（见下）：高风险 ≥2 评审子代理交叉、主智能体只汇总；M 档 1 路子代理 + 机器门禁 | 检查员会话独立对标；工人会话提交前按风险档自审（高风险 ≥2 交叉；M 档 1 路 + 机器门禁）。无独立检查员会话时：工人风险档自审 + 调度抽检即为满足；本批有批级评审时，批级评审充当 M 档第二视角（批末补强、不阻塞单票销单） | 用户自检（可豁免子代理交叉；高风险单须在验收说明中显式接受风险；销单仍须填节点对标结论） |
| 收账归属（销单/时记/changelog） | 本会话统一收 | 工人会话销单与 changelog；调度会话做时记环节建/勾/收口与台账登记，不碰代码与销单 | 用户会话收 |

时记/changelog 是否必做由 `.dev-flow.json` 的 `taskchron.mode` / `changelog.mode` 决定；未配置时按项目自身规范，不硬性要求，环节归属不变。

**形态 A 的「单会话」指角色不分离**（主会话兼实现与汇总），不等于一条会话硬扛多单；每单结束按 `09-conductor.md` §5 做上下文清空或新开会话，需要搬运即 `/handoff`。

**单会话形态（A/C）的每轮汇报**：没有路由会话，收尾按 `09-conductor.md`「每轮汇报四块」执行——首块写「🚧 本会话正在干的活」（本会话正在施工的活；无则写无），再跟②需要用户拍板/动手的事（无则写无；未处理前每轮重复）③下一步可开的任务（按依赖/优先级，注明前置是否满足），至少用前三块；第四块（阶段性综合评审触发点）在批量落地时补上。

### 评审铁律（按风险分档；形态 A 通用，形态 B 的工人会话同样适用）

**先判档再派评审**——档位按工单影响面与变更性质取，拿不准升档：

| 风险档 | 判据 | 评审强度 |
| --- | --- | --- |
| 高风险 | L 档 / 触及信任边界（安全边界）/ 协议·数据·不可逆变更 | **≥2 个评审子代理交叉**；主智能体只汇总，不自审 |
| 中风险 | M 档（单模块功能/修复） | **默认 1 个评审子代理 + 机器门禁**（测试/覆盖率/审计/状态行/销单机检）；本批另有批级评审（05 完成评审 3 路 + 裁判，不因 M 档降级）时，批级评审充当第二视角，批末补强、不阻塞 M 单销单；没有批级评审时，用户可显式要求第二路（不默认加） |
| 低风险 | S 档（单文件/半天内/无行为面/纯文案样式） | 按 S 规则自检 + 验收说明，不强制子代理 |

- **评审输入**：改动 diff + 对应漏洞/需求描述 + 技能（或模块）现有结构路径；派了评审子代理的，每个子代理各走完整「规格符合性 + 代码质量」两段——与 SDD 自带两段评审是叠加关系，不因分档豁免两段；交叉强度按上表（高风险 ≥2、M 档 1 路、S 档自检），不因两段另行加派。
- **主智能体只汇总意见与处置，不亲自下评审结论**——防串供；**「不许只派 1 个」仅约束高风险档**，M 档 1 路是默认值、不是违规。
- **M 档的机器门禁不可省**：测试/覆盖率/审计/状态行/销单机检等能机检的一律机检，机检零红才可销单；机器门禁不能替代那 1 路子代理。**节点对标结论按销单门禁做结构核对**（调度/检查员核对；A/C 形态由主会话自查；`issue-audit` 当前未解析该节，不得冒充机检）。
- **修复批**：先按本批风险档判档（高风险仍 ≥2 路；M 档 1 路 + 机器门禁；S 档自检）。04 的工单级修复批评审通过后**不再单开「窄复评」**，除非修复触及信任边界或原批审发现逻辑问题——此时须在报告里写明理由再开。05 的「必须修修完再跑一轮、连续两轮无新增」是功能级完成评审的收敛轮，不受本条免窄复评约束。
- 意见冲突时：列分歧点报调度会话（无调度则报用户）裁决，不自行取舍；形态 B 下检查员会话结论与工人自审结论相左时，同样报调度会话裁决。

### 入口切换检查清单（旧流程每一步 → 新流程归谁，缺行即停）

切换流程入口（如 geo-flow → dev-flow）时的核对方法：**先读旧入口手册（如 `geo-flow/SKILL.md`），枚举它的全部环节，逐环节在下表找新归属；旧环节在下表无对应行＝缺行，立即停下补表，不得静默带过**。表内行归属列空着同样即停。

以 geo-flow 六步为示例映射（其他旧入口照此法自建对照表）：

| geo-flow 旧步骤 | dev-flow 新归属（A 单会话 / B 跨会话 / C 单人） |
| --- | --- |
| 领单 | 工单就绪即领：A 本会话 / B 工人会话 / C 用户会话 |
| 复述工单 | 节点流程第 1 步，归属同上 |
| tdd@接缝 | 节点流程第 2-3 步，归属同上 |
| 定向验证 | 节点流程第 4 步 + 项目门禁，归属同上 |
| 双轴评审 | 节点流程第 5 步节点对标：A 本会话按风险档（高风险 ≥2 交叉；M 档 1 路 + 机器门禁）/ B 检查员对标 + 工人按风险档自审 / C 用户自检——**最易静默流失的一行** |
| 收工（项目收工门禁，如 `npm run wt:done`） | 销单 + 交报告（B 形态报告落 `evidence/<ticket>-report.md` 头部并提交，唯一回传通道见 09 §3）：A 本会话 / B 工人会话 / C 用户会话；B 的收账与时记环节勾/收口由调度会话做 |

dev-flow 六步中不属于旧流程的新增环节（如 final-review 3 路、实机验收）不缺行，直接按各阶段分册执行。

> 实证（一次 L 档跨会话跑批）：流程入口切换时每单评审环节容易静默流失——工人以为调度查、调度以为工人查，两边都没做。对策固化为两道硬门禁：开工门禁＝工单缺「本单评审执行者与方式」字段不开工；销单门禁＝工单缺「节点对标结论」节或三项任一为空不得置 done（字段与节的定义见 `templates/issue.md` 工单模板与 `references/03-tickets.md` 工单格式）。

### 多会话上下文治理（形态 B 核心；A/C 参考）

形态 A/C 不适用「零执行」条（主会话/用户本就身兼执行）；A/C 取落盘精神：执行细节落盘、汇报只给结论行＋落盘背书。

- **调度会话零执行**：不跑实现/验证命令、不派本会话子代理干活、不做代码/产物探查——查状态以外的一切探查（含只读 grep）都算执行，需要查就写进派单令让工人回报。允许的动作只有：记账（`state.json`/工单状态行/台账登记）、只读状态与队列查询（`flow-status.mjs`、项目队列命令（如有）、`taskchron-payload.mjs` 等不产生执行细节的脚本）、裁决、转发派单令、时记环节建/勾/收口（03 建环节、04/05 勾、验收后收口；不建工单级条目，见 08；计划外补记按项目规范由工人会话自理；`taskchron-payload.mjs` 仅旧功能 6 里程碑补录，历史/降级）、抽检（＝落盘背书的结构性核对：结论行对应的节/文件存在且非空，不亲自读全量 diff、不跑命令）。调度会话一旦开始执行，就已是工人会话——另开会话干，不身兼两职；拿不准某动作算不算执行或发现已违规，报用户裁夺。
- **执行细节只存在于工人/检查员会话**：命令输出、diff、评审过程留在执行会话与其落盘产物（`specs/<feature>/` 的工单文件、`evidence/`、`state.json`、`decision-log.md` 等）里，不回灌调度会话上下文；过程级细节不强制落盘，落盘归口＝节点对标结论（结论级）+ `evidence/`（证据级）。
- 调度会话需要的执行信息＝工人汇报中的结论行（销单状态、评审结论、剩余风险），每行须有落盘文件背书（结构性核对，同抽检口径；裁决所需的分歧摘要除外，仍须最小化）——「我检查过了」不算证据。

## 接线检查清单（重点）

| 类型 | 查什么 |
| --- | --- |
| 前端入口 | 菜单/按钮/路由/快捷键是否真的注册；点击是否走到新代码 |
| 状态 | store 是否更新；组件是否订阅；是否残留旧状态 |
| IPC | 命令是否在 `lib.rs` 单源宏清单 `host_invoke_handler` 注册（一处即可，debug/release 展开同一宏）；参数/返回值类型是否一致 |
| 后端 | Tauri command 名称、权限、错误码；Python 入口是否可达 |
| 契约/端口 | 设计定义的接口/Port/Protocol 是否有**生产代码消费者**（grep 生产目录，排除定义处与测试）；零消费者＝死契约，即停——接线或登记偏差，不许当装饰 |
| 覆盖台账 | 改动覆盖/端口/映射类台账的工单，勾选前必须附对账命令红绿输出（禁手改状态字段）；无对账脚本的台账不得标 covered（口径见 05-final-review 覆盖类台账机器对账） |
| 资源 | 打包资源清单、插件依赖、安装版是否包含新文件 |
| UI | 空状态/加载/错误/禁用态；是否遮挡地图；主题切换是否正常 |
| 回归 | 同类旧功能是否仍可用；旧数据是否仍能打开 |

## 门禁

- 开工门禁：工单（或简报）必含「**本单评审执行者与方式**」字段，缺失不开工。存量单开工前按形态表补齐（无派单令默认形态 A），重开/续做视为新开工；派单令形态与字段值不一致时**形态以派单令为准并回改字段；评审强度取风险档与派单令的较强值**；取值不得弱于本单风险档对应的评审强度（评审铁律）。**风险档由工单「影响面/安全触发」判定，派单令只能加强不能降低；高风险单不得由调度会话降档，用户显式接受风险须在工单历史/调度台账写明理由。**
- 销单门禁：工单「**节点对标结论**」节填齐（评审执行者/必须修清单/处置记录三项非空，占位符未替换视为空）后才许置 done（blocked/cancelled 单不适用）；**M 档另须「评审执行者」项含机器门禁命令与零红结论**；结论中的评审执行者弱于头部「本单评审执行者与方式」承诺的强度不得销单——补足评审，或经用户显式降档并回改头部字段（高风险单按开工门禁的降档限制执行）。
- 销单机检（硬拦，本技能 `scripts/issue-audit.mjs`，绝对路径运行，默认 `--phase final-review`）：
  1. **状态行规范**：首 token 必须是 `pending|in-progress|done|blocked|cancelled`；`✅` 等非规范写法直接红（不再跳过整张单）。
  2. **扫描范围**：`T-13A/T-13B1/T-13B2` 等字母后缀工单必须入扫描；`T-*.md` 但不合规范的文件红。
  3. done 工单验收清单必须全勾且至少一项；状态翻 done 不得与 feat/fix 同提交、不得触碰代码文件（销单须独立 docs/chore 收口提交；`docs/design/**/*.yaml|yml` 按 `audit.designDocGlobs` 显式白名单放行，覆盖表 yaml 不算代码）。
  4. **设计决策落点**：每个「覆盖」D-ID 必须在 `traceability.md` 设计决策映射节有落点（决策正本/兑现工单/证据），或已登记 `design-deviation.md`；缺映射节/缺行/映射行仍 planned 而工单 done = 红。
  5. **状态同步**：issue 状态行 ↔ `tasks.md` 索引行 ↔ `traceability.md` AC/决策行必须一致；不一致 = 红。
  6. **豁免来源**：`issue-audit 豁免` 必须是独立评审/档案会话写入，带「独立重签」等签名 + 仓库内可查报告路径；工人自写/无签名/路径不存在 = 红，不得降级 NOTE。
  任一红＝销单未过。
- 每张工单：验证命令绿（M 档另需机器门禁零红）+ 节点对标必须修全部处置完毕（已修/误报/延后，见节点对标结论） + 证据齐全。
- 全部工单完成：`traceability.md` 每条 AC 有证据；无 `BLOCKED`。
- 更新状态：`stage=final-review`，`nextAction=3 路完成评审`。

## 跨仓库协作（改别人仓库前必读）

动另一个仓库/系统的任何落盘内容前，先完成三件事：

1. **读目标仓的交付规约**：`AGENTS.md`、分支/合并模型、门禁命令、变更日志要求——一整套继承，不只看代码风格。
2. **走目标仓的正门**：需要认领槽位就认领、需要工作分支就开分支、需要 changelog 就写；不要用“不想打扰并行会话”作为绕过协议的理由——绕过合并预期恰恰是最打扰的方式。
3. **写完对账**：目标仓的门禁/状态/台账按它的规矩收尾；跨仓改动在自己的交付汇报里单列“目标仓 + 遵循了哪些规约”。

判断标准：如果目标仓有自己的 AGENTS.md 或开发流程文档，**它优先于本技能与本仓习惯**；两边冲突时，先问目标仓负责人，不自行取“等效捷径”。

## 常见错误

| 错误 | 后果 | 纠正 |
| --- | --- | --- |
| 先写实现再补测试 | 测试证明不了行为 | 先红后绿 |
| 测试 mock 内部协作者 | 重构就红 | 只 mock 系统边界 |
| 实现时顺手重构无关代码 | diff 爆炸、评审失焦 | 预重构单独成单 |
| 只跑单测不跑集成 | 没接线/跑不通 | 节点检查加接线清单 |
| 发现设计错了悄悄改 | 设计和代码对不上 | 停下回设计阶段 |
